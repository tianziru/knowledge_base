# 灵犀智库 · 项目背景

## 1. 一句话定位

**灵犀智库**是一套面向「设备 / 产品说明书」场景的智能问答系统：管理员把手册类文档导入知识库，终端用户用自然语言提问，系统优先依据已入库文档作答，必要时再联网补充。

产品形态上拆成两端：

| 端 | 端口 | 职责 |
|----|------|------|
| 导入后台 | `8000` | 文档上传、解析、切分、向量化、入库与任务监控 |
| 问答前台 | `8001` | 多轮对话、商品/设备确认、检索融合、答案生成 |

---

## 2. 要解决什么问题

传统说明书使用方式存在明显摩擦：

1. **查找成本高**：PDF / Word 篇幅长、目录层级深，用户要翻页或全文搜索关键词，很难快速定位「如何校准」「报错代码含义」等操作步骤。
2. **跨文档难统一**：多型号、多版本手册分散存放，客服或售后人员需要先判断「问的是哪款产品」，再翻对应文档。
3. **纯大模型不可靠**：直接问通用 LLM 容易编造参数与步骤；企业需要**以自家说明书为准**的可控回答。
4. **非结构化为主**：说明书以叙述、图示、注意事项为主，并非整齐的数据库字段；适合「检索增强生成（RAG）」，而不是先做完整业务中台。

因此本项目的核心目标是：

> 把非结构化手册变成可检索的知识切片，在对话中先锁定产品/设备，再据此检索并生成可溯源的回答。

---

## 3. 业务场景与角色

### 3.1 典型用户问题

- 设备如何开机 / 配对 / 校准？
- 某故障现象或报错如何排查？
- 日常维护、安全注意事项是什么？
- 参数、接口、配件说明（以手册记载为准）

系统人设（见 `prompts/answer_out.prompt`）：**灵犀智库客服助手**，围绕设备使用、维护、故障排查作答；知识库与联网结果并存时，**以说明书为准**。

### 3.2 角色分工

| 角色 | 行为 |
|------|------|
| 知识管理员 | 在导入后台上传 PDF/MD/TXT/DOCX/PPTX 等，查看任务进度与统计 |
| 终端用户 / 客服 | 在问答页提问，通过多轮对话澄清型号后获得步骤与注意点 |

### 3.3 领域演进（现状）

项目从**设备 / 产品说明书 RAG**起步；过程中曾短暂尝试工商信息类资料，后已恢复以设备手册为主。当前品牌与提示词、前后端文案均统一为「灵犀智库」，业务主键仍是「商品 / 设备名称（item_name）」。

---

## 4. 为什么采用当前技术路线

### 4.1 双服务 + 双 LangGraph

- **导入**与**查询**负载特征不同：导入长耗时（PDF 解析、向量化），查询偏交互与流式输出。
- 拆成独立 FastAPI 进程（8000 / 8001），各自一套 LangGraph 工作流，避免互相拖垮；共享 `clients` / `lm` / `conf` 等基础设施代码。

### 4.2 以向量知识库（RAG）为主，而非知识图谱

说明书问答的主路径是「定位段落 → 归纳步骤」，与 **Milvus 稠密 + 稀疏混合检索**高度匹配。

知识图谱（Neo4j）在仓库中仅有配置与查询占位节点，**未形成真实导入/查询业务**。对当前「按型号查手册」场景，完整上图谱成本高、收益不明确；更合适的补强是商品名索引、别名表与检索质量，而非强行上图。

### 4.3 「商品 / 设备名」作为业务主键

导入时用大模型从文档前部切片识别 `item_name`，写入：

- `kb_item_names_v2`：供问答侧「确认查询商品」
- `kb_chunks_v2`：每个切片带同一 `item_name`，支持按型号过滤与幂等覆盖（同名重新导入会清理旧切片）

这解决了「用户问得模糊、库里有多型号」时的歧义：先确认设备，再检索，避免串型号。

### 4.4 多路检索与兜底

查询侧在商品确认后并行：向量检索、HyDE、联网搜索（MCP）、以及预留的图谱查询桩；经 RRF 与本地 Rerank 后生成答案。  
设计意图是：**库内有手册时优先用手册；库内不足时用联网补全，并提示以说明书为准**。

## 5. 系统能力边界（当前）

### 5.1 已具备

- 多格式导入：PDF（MinerU）、MD、TXT、DOCX、PPTX；导入后台壳子（概览 / 导入 / 任务 / 格式说明）
- PDF 图文：解析出的图片可经多模态摘要后上传对象存储，并改写 Markdown 链接
- 标题感知切分 + 长短块整理
- BGE-M3 双向量入库与混合检索
- 会话历史（MongoDB）与流式问答（SSE）
- 任务状态与节点进度默认写入 `data/tasks.db`（SQLite）并热缓存；配置 `REDIS_URL` 后改用 Redis 权威存储 + Pub/Sub SSE，供多实例共享

### 5.2 明确不做或未做完

- 无登录鉴权与多租户权限
- 知识图谱未真正接入
- 未配 Redis 时多 worker 不共享热缓存，需共用 `data/tasks.db` 并注意写锁；SQLite 下进行中任务在进程重启后记为失败。Redis 下用 lease 回收孤儿任务（读路径懒检测），**启动不批量**把进行中任务标 failed
- 不做通用搜索引擎或替代完整售后工单系统

## 6. 外部依赖概览

| 依赖 | 用途 |
|------|------|
| MinerU 云 API | PDF → Markdown |
| MinIO | 原稿与图片持久化访问 |
| Milvus | 商品名与文档切片向量库 |
| BGE-M3 / Reranker | 向量化与重排序 |
| DashScope 兼容 LLM / VL | 识别商品名、图片摘要、改写、生成答案 |
| MongoDB | 聊天历史 |
| Redis（可选） | 多实例共享任务进度与 SSE；未配置则回退 SQLite |
| 百炼 WebSearch MCP | 联网检索兜底 |
| Neo4j | 仅环境预留，业务未用 |

---

## 7. 项目价值小结

| 维度 | 说明 |
|------|------|
| 对用户 | 用自然语言问手册问题，少翻 PDF |
| 对运营 | 手册可增量导入、按商品覆盖更新 |
| 对工程 | LangGraph 把「解析 → 切分 → 入库 / 确认 → 检索 → 生成」拆成可观测节点，便于排障与迭代 |
| 对质量 | 答案锚定私有知识库，降低纯幻觉风险；联网仅作补充 |
